The Interface loads .effs, provides LVGL preset/sequence editing, calculates parameters and compiles FPGA programs/updates. Requirements describe intentions, not implementation.

David requires:

- Canonical descriptor-driven numeric policies for instruction arguments. Descriptors specify each argument's permissible format subset, signedness, clamping and instruction-level send post-processing, including compositions such as 2f−1 or erf. A joint resolver maps the argument range/format possibilities, concrete expression/channel/constant realizations and chosen policies to concrete argument encodings and the instruction format field. Preserve each expression register's resolved float-to-binary conversion through initial programming, dependencies, queued writes and live updates. Analyze the range after send transforms and use the same transforms for every send. No ad hoc SVF branch should shortcut this model. The existing expression and descriptor architecture should be extended minimally; SVF cutoff uses David's selected signed Q15 encoding, with nonnegative handling and independently formatted damping. Preserve the matching RTL normalization. Concrete types and current policies belong to the fixed-point owner; further instruction contracts require their own hardware evidence. how/does/the/interface/choose/fixed/point/formats.md owns source and design detail.

- A useful automated C test suite, coordinated with the shared effect-verification specification in the superproject.
- Preserve working Danger Button confirmation behavior and raise the confirmation buttons slightly within the popup. David accepted the standard LVGL message-box footer/padding adjustment; no custom widget or broader redesign is required. Keep reusable desktop software-in-the-loop interaction and screenshot utilities for evidence-driven UI work. Implementation and acceptance belong to what/does/kest-button/implement.md and how/to/inspect/the/desktop/ui.md.
- Remove deprecated code, explicitly including the kest_representation framework. Severely tidy and repackage the old DMA/readback subsystem, preserving useful FPGA memory readback. Scratchpad reads provide a stream of live DSP values, and consumers use the latest available sample. Keep dispatched reads simple: attach a callback that atomically writes the destination and, if needed, marks that a value landed. The control-loop task makes an honest attempt to refresh at the needed cadence; SPI owns wire transactions and invokes the callback. Do not add request tokens, reply correlation, deadline/retry tracking or a parallel polling framework for this stream. Mark resource payloads for deletion and let the existing control loop handle retirement; stop new work on marked resources and preserve queued callback destinations until completion. Preserve destination lifetime through callback completion, retain the last good sample on failure and integrate with existing task responsibilities. Normal operation assumes the FPGA works; fix bugs rather than adding permanent defensive workarounds. A missed read does not stop DSP/UI operation or trigger recovery machinery: the next ordinary read is another refresh opportunity. Remove redundant disabled machinery.
- Make allocation strategies consistent and actually use the existing partial support for swapping strategies where it matters. Exact allocation sites, ownership/lifetime contracts and strategy selection remain to be agreed.
- Provide frictionless discovery at huge-library scale, with metadata-driven category views, search and composable logical filtering. what/is/the/effect/discovery/specification.md owns David's complete interaction, metadata, logic and dependency requirements; define its open semantics and qualify target responsiveness before acceptance.
- Add setlists: an ordered sequence of sequences, providing a level above the existing sequence abstraction. David has specified the name and hierarchy; progression between sequences, end-of-sequence/end-of-setlist behavior, editing, persistence and missing/deleted sequence handling remain to be defined. Do not infer automatic advancement, looping or recursive nesting.
- Load .effs asynchronously: a background task populates the effect list during startup. Implement this as reusable functionality callable later to flush and repopulate the list for SD-card swaps or clears. During refresh, update everything that remains. A changed descriptor file with the same cname represents an update of that effect, not a separate effect identity. This is one required part of reconciliation, not a complete behavior contract. Thoroughly define retained/removed/new descriptors, existing and active preset/effect migration, parameter/setting/resource/code changes, concurrency, cancellation and failures before implementing refresh. Do not infer the remaining policies from this identity rule.
- Provide a sensible UART debug/control command suite accessible over USB. Include filesystem controls for uploading/loading, deleting and moving .effs, plus utilities for operating and diagnosing the device so agents can perform HIL testing. A substantial part must drive the actual UI with phantom presses, dragging and scrolling through normal LVGL input handling, so HIL exercises the full system. The initial staged filesystem transfer contract belongs to how/to/control/the/interface/over/uart.md; live loading/refresh and broader diagnostic coverage remain open. Frame-rate tuning is deferred; preserve the existing refresh baseline for now.

- Horizon: add a boot splash screen. Visual design, startup placement and dismissal behavior remain unspecified; no priority change is assigned.

- Horizon: optimize .eff instruction order for the actual hardware using the symbolic instruction-sequence representation that David reports is now available. Its purposes include clearer representation and reducing excess SPI traffic from naive encoding; scheduling is an additional future use. Preserve instruction dependencies and observable effects while targeting measured pipeline latency, stalls and throughput. The representation's current implementation and scheduling acceptance criteria have not been checked in this requirements-capture pass; inspect them before implementation. No immediate implementation or priority change is requested.

The lightweight one-pipeline DSP simulator, full one-pipeline Verilator verification and physical HIL requirements are owned by the superproject's what/is/the/effect/verification/specification.md. Firmware must support that loop.

Other effect lifecycle, control mapping, UI, persistence and live-update acceptance criteria remain partial. Board-specific display/touch, footswitch, SPI-enable, backlight and audio-backend requirements remain governed by the superproject's hardware brief and circuit owners.
